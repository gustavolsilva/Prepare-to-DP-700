A Crise dos Silos de Dados e o Pesadelo da Replicação

Imagine o seguinte cenário em uma grande corporação:

O time de ingestão usa Azure Data Factory para carregar dados brutos em um Data Lake. O time de engenharia usa Databricks para limpar esses dados e gerar tabelas Delta. Depois, outro time roda scripts para carregar essas tabelas dentro de um Data Warehouse dedicado (Synapse ou Snowflake) para que os analistas de negócios consigam rodar consultas T-SQL. Por fim, o time de BI cria relatórios no Power BI que precisam importar tudo de novo para a memória do Analysis Services às 6h da manhã.

O resultado? Os mesmos dados são copiados e pagos quatro vezes em contas de armazenamento diferentes. Quando um dado sensível precisa ser deletado por exigência da LGPD/GDPR, o time gasta semanas caçando réplicas. Se um pipeline quebra às 03:00, os diretores abrem o dashboard de manhã e encontram dados desatualizados. O Microsoft Fabric foi criado pela Microsoft exatamente para acabar com essa fragmentação.

A Arquitetura do Microsoft Fabric e Seus Motores Analíticos

Clique em qualquer um dos motores no diagrama interativo abaixo para inspecionar sua responsabilidade técnica e formato de armazenamento no OneLake:

O Microsoft Fabric é uma plataforma analítica no modelo Software as a Service (SaaS). Ele consolida todas as ferramentas de dados da Microsoft sobre uma fundação única de armazenamento chamada OneLake. Ao contrário das arquiteturas tradicionais, onde cada ferramenta mantinha seu próprio formato de arquivo proprietário, o Fabric estabelece o formato aberto Delta Lake (Parquet colunar com histórico de transações ACID) como o padrão universal.

Isso permite que um time de cientistas processe dados em Python através do Spark Notebooks, um time de analistas de negócios consulte as mesmas tabelas via T-SQL no Data Warehouse, um time de IoT consuma telemetria em alta frequência no Eventhouse via KQL, e os relatórios do Power BI acessem esses dados via Direct Lake diretamente na memória, sem nunca mover ou duplicar um único arquivo.

Toda a computação é quantificada através de Capacity Units (CUs). O Fabric implementa um algoritmo de Smoothing com janela móvel de 24 horas, permitindo que picos pontuais de processamento não causem bloqueios ou custos imprevistos. Para o exame DP-700, é fundamental compreender a separação entre o Lakehouse (focado em código e arquivos com endpoint SQL somente leitura) e o Warehouse (focado em T-SQL com suporte transacional completo de escrita).

Pense no Microsoft Fabric como um "pacote Office para dados gigantes". Antigamente, quem trabalhava com dados precisava instalar e configurar vários programas complicados que não conversavam entre si. No Fabric, tudo abre em um único site no seu navegador.

O coração do Fabric é o OneLake. Ele funciona exatamente como o OneDrive da sua empresa, mas em vez de guardar documentos de texto, ele guarda tabelas de dados. E o grande segredo da velocidade do Fabric é o armazenamento em colunas (Parquet):

  • Banco de cadastro (Linhas): Se você tem uma planilha com 1 milhão de clientes e quer apenas somar as idades, o computador lê nome, CPF, endereço e telefone de cada linha, desperdiçando tempo.
  • Banco analítico (Colunas): No OneLake, a coluna idade é guardada separada em um bloco próprio. O computador lê direto apenas os números da idade e responde em menos de um segundo.

No dia a dia de engenharia de dados, a maior vantagem prática do Fabric é a redução de código de movimentação. Ao criar um Lakehouse, você ganha automaticamente duas pastas essenciais:

  • /Files: Destinada a dados brutos não estruturados ou semi-estruturados (arquivos CSV, JSON, imagens, logs brutos) consumidos via PySpark.
  • /Tables: Destinada exclusivamente a tabelas Delta gerenciadas. Qualquer arquivo Delta gravado aqui é registrado automaticamente no catálogo do Fabric e fica disponível instantaneamente no SQL Analytics Endpoint para consultas T-SQL.

Para orquestração, você utiliza o Data Factory, que une atividades de cópia de alta performance (com suporte a conexões locais via On-premises Data Gateway) e Dataflows Gen2 para limpezas visuais em Power Query que gravam direto no Lakehouse ou Warehouse de destino.

Para obter a pontuação máxima no exame DP-700, você precisa dominar o Decision Matrix da Microsoft entre os motores de armazenamento:

  • Lakehouse vs. Data Warehouse: O Lakehouse suporta código aberto (Spark, PySpark, Scala, R) e manipulação de arquivos. Seu SQL Analytics Endpoint é estritamente somente leitura. Se o enunciado da prova exigir suporte a comandos DDL/DML em T-SQL clássico (ex: INSERT INTO, UPDATE, MERGE via T-SQL com transações atômicas multi-tabela), a única resposta correta é o Fabric Warehouse.
  • Virtualização com OneLake Shortcuts: Se o cenário exigir expor dados já existentes em um bucket AWS S3 ou ADLS Gen2 externo dentro do Lakehouse com o menor esforço e sem duplicar dados, a resposta da prova é criar um OneLake Shortcut, e não um pipeline de cópia.
  • Direct Lake Mode: Permite que relatórios do Power BI consultem as tabelas Delta sem realizar a tradicional importação (evitando atrasos de refresh agendado) e sem a lentidão do DirectQuery tradicional.

Sob o capô, o Microsoft Fabric implementa uma série de otimizações de nível de sistema operacional e formato binário:

  • Native Execution Engine (Velox & Apache Gluten): O runtime do Spark no Fabric não roda pipelines do Spark SQL puramente na JVM. As etapas físicas de shuffle, projeção e hash joins são delegadas para uma biblioteca nativa em C++ altamente vetorizada com instruções SIMD.
  • Algoritmo V-Order: É uma ordenação proprietária no momento da gravação de arquivos Parquet. O V-Order reorganiza os row-groups e dicionários de colunas para acelerar leituras analíticas em até 10x nos motores SQL e Direct Lake.
  • Concorrência e Transações: O Warehouse do Fabric utiliza snapshots baseados no log do Delta com controle de concorrência otimista (OCC). Operações DDL e DML produzem novos commits no Delta Log, mantendo compatibilidade total com o ecossistema aberto.

Para o Chief Data Officer (CDO) e diretores de engenharia, o Fabric altera substancialmente a estrutura de custos de nuvem da empresa:

  • Previsibilidade de FinOps via Smoothing: Em nuvens legadas, um pico de consumo de 10 minutos forçava a contratação de clusters caros dimensionados para o pico. Com o Smoothing de 24 horas do Fabric, os picos de jobs em lote (background) são distribuídos uniformemente ao longo do dia, permitindo contratar SKUs menores (ex.: F64 em vez de clusters dedicados gigantes).
  • Eliminação de Custos de Egress: O OneLake virtualiza dados através de Shortcuts (inclusive em clouds concorrentes como AWS e GCP), evitando transferências redundantes de petabytes.
  • Governança com Microsoft Purview: Sensitivity Labels (rótulos de confidencialidade) aplicados no OneLake propagam-se automaticamente até os relatórios do Power BI e consultas SQL, garantindo conformidade regulatória sem silos.

Exercício Prático: Provisionar Capacidade Fabric e Explorar Lakehouse vs Warehouse

Guia passo a passo para executar diretamente na plataforma em nuvem do Microsoft Fabric (ou em simulação local).

📋 Cenário do Laboratório

A Contoso Global Retail está migrando sua arquitetura legado para o Microsoft Fabric. Como Engenheiro de Dados, você deve criar um Workspace sob uma capacidade Fabric, provisionar um Lakehouse para ingestão de dados em arquivos Delta e um Data Warehouse para relatórios analíticos corporativos com transações T-SQL ACID.

🔑 Pré-requisitos para Execução no Portal

  • Navegador web moderno (Edge, Chrome ou Firefox).
  • Acesso ao portal Microsoft Fabric (app.fabric.microsoft.com).
  • Capacidade ativa do Fabric (licença Fabric Trial gratuita ou capacidade corporativa).
  • Um Workspace configurado no modo de capacidade Fabric.
1

Acessar o Portal e Criar o Workspace com Capacidade Fabric

  1. Acesse o portal do Microsoft Fabric e efetue login.
  2. No canto inferior esquerdo, clique no ícone de Engenharia de Dados (Data Engineering).
  3. No menu lateral, clique em Workspaces e crie um novo workspace nomeado DP700_Foundations_Lab.
  4. Nas configurações avançadas, assegure-se de vincular o workspace a uma Capacidade Fabric (Trial ou F-SKU).
  5. Clique em Aplicar.
🔒 https://app.fabric.microsoft.com/groups/new-workspace
📸 Captura do Portal: Configurando workspace vinculado à capacidade Fabric e selecionando a experiência de Engenharia de Dados.
2

Criar o Lakehouse e Ingerir Arquivos Brutos via PySpark

  1. Dentro do workspace, clique em + Novo item e selecione Lakehouse.
  2. Nomeie como lh_retail_raw e clique em Criar.
  3. Clique em Abrir notebook > Novo notebook.
  4. Execute o código PySpark abaixo para carregar dados brutos e salvá-los como tabela Delta:
PYTHON (PYSPARK) — LAKEHOUSE NOTEBOOK MICROSOFT FABRIC CODE EDITOR 
# Ingestão de dados brutos de vendas no Lakehouse
dados = [
    (1, "Notebook Gamer", 4500.00, "Sul"),
    (2, "Monitor UltraWide", 1800.00, "Sudeste"),
    (3, "Teclado Mecânico", 350.00, "Sul")
]
colunas = ["ProdutoID", "NomeProduto", "Preco", "Regiao"]

df = spark.createDataFrame(dados, colunas)
df.write.format("delta").mode("overwrite").saveAsTable("raw_produtos")
print("✅ Tabela raw_produtos gravada com sucesso em Delta Lake!")
3

Criar o Data Warehouse e Executar Transações T-SQL ACID

  1. Retorne ao workspace, clique em + Novo item e selecione Data Warehouse.
  2. Nomeie como dw_retail_corporate e clique em Criar.
  3. Na barra de ferramentas, clique em Nova consulta SQL e execute o script T-SQL com suporte a transações multi-tabela:
T-SQL — FABRIC DATA WAREHOUSE MICROSOFT FABRIC CODE EDITOR 
-- Criação de tabela relacional com integridade no Warehouse
CREATE TABLE dbo.DimProduto (
    ProdutoID INT NOT NULL,
    NomeProduto VARCHAR(100) NOT NULL,
    Preco DECIMAL(10,2) NOT NULL,
    Regiao VARCHAR(50) NOT NULL
);

-- Transação ACID atômica
BEGIN TRANSACTION;
INSERT INTO dbo.DimProduto (ProdutoID, NomeProduto, Preco, Regiao)
VALUES (1, 'Notebook Gamer', 4500.00, 'Sul'),
       (2, 'Monitor UltraWide', 1800.00, 'Sudeste');
COMMIT TRANSACTION;

SELECT Regiao, SUM(Preco) AS TotalVendas FROM dbo.DimProduto GROUP BY Regiao;

⚠️ Atenção para o Exame DP-700:
No exame DP-700, lembre-se: o Lakehouse é focado em arquivos e manipulação de Big Data com Spark (possuindo SQL Endpoint somente leitura), enquanto o Data Warehouse oferece suporte transacional completo DDL/DML, multi-table transactions ACID e segurança avançada (RLS/CLS).

Pontos Críticos para a Prática e para o Exame DP-700

📝 Síntese dos Pontos Críticos Aprendidos:

  1. OneLake como Pilar Central: O OneLake elimina a cópia redundante de dados entre Data Lake, Data Warehouse e relatórios de BI através do formato aberto Delta Parquet.
  2. Lakehouse vs. Warehouse na Prova DP-700: O SQL Analytics Endpoint do Lakehouse é somente leitura. Se um cenário exigir operações DDL/DML e transações ACID via T-SQL, a escolha correta é sempre o Fabric Data Warehouse.
  3. Smoothing de 24 Horas: O Fabric amortiza o consumo de operações em segundo plano (background) ao longo de 86.400 segundos, permitindo rodar jobs intensos sem interrupções por falta momentânea de recursos.
  4. Direct Lake no Power BI: Elimina a necessidade de atualizações de dados periódicas ao ler diretamente os metadados e arquivos Delta do OneLake na memória do Analysis Services.
