A Matriz Oficial de Decisão Arquitetural do Microsoft Fabric

Um dos maiores pontos de falha no Exame DP-700 ocorre quando os candidatos tratam o Fabric Lakehouse e o Fabric Data Warehouse como produtos redundantes. Eles foram concebidos com propósitos técnicos complementares e motores de execução inteiramente distintos sobre a mesma camada unificada de armazenamento OneLake.

Tabela Comparativa Rigorosa dos 4 Motores de Dados do Fabric

Critério / Propriedade Fabric Lakehouse Fabric Data Warehouse Fabric Eventhouse Fabric SQL Database
Motor Principal Apache Spark Polaris (T-SQL Distribuído) Kusto Engine (KQL) Azure SQL Serverless
Gravação de Dados (DML) PySpark, Scala, Spark SQL T-SQL DML Completo Eventstreams / Ingestion API T-SQL OLTP Completo
SQL Endpoint Somente Leitura (Read-Only) Leitura e Escrita Total KQL / T-SQL (Read-Only) Endpoint TDS Relacional
Tipos de Dados Suportados Estruturados, Semiestruturados e Arquivos Brutos (Files) Tabelas Estruturadas com Tipagem Estrita Séries Temporais, Logs e JSON Dinâmico Esquema Relacional Normalizado
Segurança Granular OneLake Data Access Roles RLS, CLS, DDM em T-SQL Row-Level Sharing em KQL RLS, CLS, Always Encrypted
Papel na Arquitetura Medallion Bronze e Silver (e Gold Data Science) Gold (Star Schema corporativo e BI) Camada de Streaming e Telemetria Sistemas Operacionais de Origem

A Regra de Ouro do SQL Endpoint no Lakehouse

Toda tabela Delta gravada na pasta Tables/ do Lakehouse é imediatamente mapeada de forma automática para o SQL Analytics Endpoint.

Isso permite que ferramentas de BI e usuários de SQL executem comandos SELECT, criem VIEWS lógicas e configurem medidas. No entanto, se um usuário tentar executar INSERT, UPDATE, DELETE ou MERGE diretamente pelo SQL Endpoint, o sistema retornará um erro imediato de permissão. O SQL Endpoint do Lakehouse é 100% somente leitura.

🌱 Como Lembrar a Diferença Facilmente?

Pense no Lakehouse como uma oficina mecânica com ferramentas pesadas de Spark para desmanchar, limpar e transformar peças brutas (arquivos bagunçados, JSONs, fotos, logs).

Pense no Data Warehouse como uma vitrine de joalheria relacional. Tudo já está limpo, organizado em gavetas numeradas (tabelas de fatos e dimensões) e pronto para ser ajustado com precisão usando a linguagem tradicional T-SQL.

🌿 Cenários de Implementação Prática no Workspace

Quando criar um Lakehouse vs. Warehouse no seu projeto:

  • Crie um Lakehouse quando: O time for composto por engenheiros Python/PySpark, houver necessidade de salvar arquivos não estruturados na pasta Files/ e para a ingestão e limpeza das camadas Bronze e Silver.
  • Crie um Data Warehouse quando: O time for especialista em SQL Server, houver procedimentos armazenados (Stored Procedures), triggers, restrições relacionais e comandos UPDATE/DELETE frequentes em tabelas analíticas.

🛠️ Pegadinhas Clássicas do Exame DP-700

⚠️ Armadilha #1 de Decisão: "A equipe precisa expor dados para analistas de dados que usarão SQL Server Management Studio (SSMS) e exigem executar scripts periódicos contendo comandos UPDATE e MERGE para reconciliação manual. Qual item do Fabric você deve provisionar?"

Cuidado com o distrator: Se uma opção for "Criar um Lakehouse e conceder permissão de escrita no SQL Analytics Endpoint", essa alternativa é falsa e impossível tecnicamente. A resposta correta é invariavelmente o Fabric Data Warehouse.

⚠️ Armadilha #2 de Decisão (Eventhouse vs Lakehouse): "Milhares de caminhões transmitem telemetria de GPS e temperatura a cada 3 segundos. A diretoria exige alertas com latência inferior a 5 segundos e retenção compactada com indexação de texto livre."

Resposta Oficial: Fabric Eventhouse (KQL). Spark Streaming no Lakehouse até suporta a ingestão, mas não atinge a latência de milissegundos com indexação de texto livre com a mesma eficiência de CUs do Kusto Engine.

⚙️ Arquitetura Interna: O Motor Polaris vs. Spark Native Engine

O Fabric Data Warehouse é alimentado pelo motor Polaris, a evolução da tecnologia de computação distribuída serverless da Microsoft desenvolvida originalmente para o Synapse Serverless SQL.

O Polaris separa totalmente o pool de computação dos dados persistidos em Delta Lake no OneLake. Durante a execução de um UPDATE ou MERGE, os nós de computação compilam o plano de execução relacional em código C++ vetorial, reescrevem os arquivos Parquet afetados e gravam o commit atômico no _delta_log com conformidade ACID completa.

🏛️ Visão Estratégica & FinOps: Sem Duplicação de Licenças

Tanto o Lakehouse quanto o Data Warehouse e o Eventhouse utilizam a mesma capacidade de Capacity Units (CUs) e gravam seus dados físicos no OneLake.

Isso significa que a organização não precisa contratar uma licença de Spark separada e um data warehouse de outro fornecedor. Todos os motores dividem a mesma piscina elástica de recursos com pagamento unificado por segundo.

Exercício Prático: Matriz Decisória - Lakehouse vs Warehouse vs Eventhouse

Guia passo a passo para executar diretamente na plataforma em nuvem do Microsoft Fabric (ou em simulação local).

📋 Cenário do Laboratório

Construir uma prova de conceito com os três tipos de armazenamento analítico no Fabric, testando qual motor deve ser recomendado para cada caso de uso corporativo.

🔑 Pré-requisitos para Execução no Portal

  • Navegador web moderno (Edge, Chrome ou Firefox).
  • Acesso ao portal Microsoft Fabric (app.fabric.microsoft.com).
  • Capacidade ativa do Fabric (licença Fabric Trial gratuita ou capacidade corporativa).
  • Um Workspace configurado no modo de capacidade Fabric.
1

Provisionar os Três Motores no Mesmo Workspace

  1. No workspace, crie um item Lakehouse (lh_telemetry_files).
  2. Crie um item Data Warehouse (dw_financial_acid).
  3. Crie um item Eventhouse (evh_sensor_live).
🔒 https://app.fabric.microsoft.com/groups/workspace/new-items
📸 Captura do Portal: Criando e organizando Lakehouses, Warehouses e Eventhouses no mesmo ambiente corporativo OneLake.
2

Comparar Capacidades de Escrita e Latência

  1. No Warehouse, execute comandos relacionais transacionais com BEGIN TRANSACTION e MERGE.
  2. No Lakehouse, execute transformações em arquivos Parquet com Spark Notebook.
  3. No Eventhouse, ingira streaming em alta velocidade e execute consultas KQL de latência de milissegundos.
🔒 https://app.fabric.microsoft.com/groups/workspace/t-sql-vs-kql
📸 Captura do Portal: Comparativo operacional de execução entre T-SQL relacional no Warehouse e KQL no Eventhouse.
⚠️ Atenção para o Exame DP-700:
Decisão de Exame: Se o requisito exigir DDL/DML nativo, integridade transacional multi-tabela e RLS/CLS, escolha WAREHOUSE. Se exigir engenharia em Python/Scala com arquivos não estruturados, escolha LAKEHOUSE. Se exigir ingestão contínua de telemetria em tempo real e consultas temporais, escolha EVENTHOUSE.

Pontos Críticos para a Prática e para o Exame DP-700

📝 Síntese dos Pontos Críticos Aprendidos:

  1. Lakehouse (Foco em Arquivos & Spark): Ideal para engenheiros Python/Scala e dados não estruturados; SQL Endpoint fornece acesso analítico somente leitura.
  2. Warehouse (Foco em T-SQL & ACID): Exigido quando o cenário necessita de transações ACID multi-tabela, Stored Procedures, DDL/DML nativo e segurança RLS/CLS no banco.
  3. Eventhouse (Foco em Streaming & KQL): Projetado para ingestão contínua em tempo real de logs, telemetria de sensores e consultas temporais ultrarrápidas.
  4. Fundação OneLake Compartilhada: Todos os três motores leem e gravam em tabelas Delta abertas sem cópias ou movimentação física de dados.
