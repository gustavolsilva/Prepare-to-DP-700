Ciclo de Vida de Engenharia de Dados em Escala Corporativa

O Microsoft Fabric integra capacidades nativas de Application Lifecycle Management (ALM) que eliminam a necessidade de exportações manuais de arquivos ou modificações manuais em produção. O ciclo de vida corporativo assenta-se em dois pilares complementares: Git Integration (para controle de versão, colaboração e branches de desenvolvimento) e Deployment Pipelines (para orquestração de promoção entre ambientes DEV, TEST e PROD com substituição automática de regras).

Topologia de CI/CD: Git Integration vs. Deployment Pipelines

Como as duas abordagens se combinam no dia a dia da engenharia de dados do Fabric.

🐙 1. Git Integration (Controle de Versão Granular)

Conecta diretamente um Workspace do Fabric a um repositório no Azure DevOps ou GitHub.

  • Serialização Declarativa: Notebooks, Pipelines, Semantic Models (PBIP) e Warehouses viram arquivos legíveis (JSON/PY/SQL).
  • Branching Strategy: Desenvolvedores criam branches individuais de feature (`feature/etl-orders`), realizam commits e abrem Pull Requests.
  • Sincronização Bidirecional: Detecta discrepâncias com status Committed, Uncommitted ou Conflict (resolvido via Commit to Git ou Update from Git).

🚀 2. Deployment Pipelines (Promoção Entre Estágios)

Gerencia formalmente o fluxo de governança corporativa entre os estágios Development, Test e Production.

  • Comparação Visual de Estágios: Identifica quais artefatos foram adicionados, modificados ou excluídos entre ambientes.
  • Deployment Rules (Regras de Implantação): Substitui automaticamente strings de conexão, servidores SQL, nomes de Lakehouses e parâmetros sem alterar o código.
  • Automação via REST API / DevOps: Pipelines de implantação podem ser disparados via Azure DevOps Extension ou Fabric REST APIs.
🎯 Foco Máximo DP-700: Deployment Rules (Regras de Implantação)
Se a questão do exame perguntar como garantir que relatórios e pipelines leiam automaticamente do banco de testes em QA e do banco produtivo em Produção sem intervenção manual, a resposta correta é: Configurar Deployment Rules no Deployment Pipeline.

Itens Suportados no Git do Fabric e Database Projects (.sqlproj)

O Fabric serializa os metadados dos itens em pastas declarativas. Para o Data Warehouse, o Fabric suporta projetos de banco de dados SQL (.sqlproj) integrados ao Visual Studio Code / Azure Data Studio. Isso permite:

  • Tratar esquemas, tabelas e views como código (Schema as Code).
  • Compilar arquivos DDL para gerar pacotes DACPAC.
  • Realizar migrações incrementais determinísticas com validação prévia de sintaxe e integridade referencial antes da aplicação em produção.

Fundamentos Simples de CI/CD e Git no Microsoft Fabric

Se você está começando em engenharia de dados, pense no Git como uma máquina do tempo e um livro de registros para todo o seu trabalho analítico.

Os Conceitos Básicos:

  • Repositório Git: A pasta central na nuvem (GitHub ou Azure DevOps) onde todas as versões dos seus notebooks e pipelines ficam guardadas.
  • Commit: Salvar um ponto no tempo com uma mensagem clara do que foi feito (ex: "Adiciona tratamento de nulos na tabela de clientes").
  • Branches: Cópias isoladas onde você pode testar novidades sem estragar o que já está funcionando para os outros.
  • Deployment Pipeline: A esteira que empurra com segurança o que foi testado em desenvolvimento para o ambiente de testes e depois para a produção.

Implementação Prática de Git e Pipelines de Implantação

Para o engenheiro de dados Pleno, a gestão de branches e as regras de implantação evitam erros humanos graves em produção:

Configurando Git Integration no Workspace

  1. Acesse Workspace Settings > Git Integration.
  2. Selecione o provedor (Azure DevOps ou GitHub) e aponte para a Organização, Projeto, Repositório e Branch desejado (ex: dev).
  3. Ao realizar alterações em notebooks ou pipelines, o botão de Git na barra de ferramentas exibe o status de alterações pendentes para commit.

Configurando Deployment Rules no Deployment Pipeline

Ao criar os 3 estágios (Dev -> Test -> Prod) no Deployment Pipeline:

  • No estágio de Test ou Prod, clique no ícone de engrenagem Deployment rules.
  • Selecione a fonte de dados (ex: SQL Database ou Fabric Lakehouse).
  • Defina a substituição: srv-dev.database.windows.net -> srv-prod.database.windows.net.
  • Defina regras de parâmetros: p_env = 'DEV' -> p_env = 'PROD'.

Arquitetura Corporativa de CI/CD & Checklist do Exame DP-700

No Exame DP-700, questões sobre ALM testam se você conhece as limitações técnicas e as melhores práticas arquiteturais:

⚠️ Itens com Suporte a Git vs. Deployment Pipelines no Fabric:
Nem todos os itens do Fabric são suportados identicamente no Git e nos Deployment Pipelines. Itens centrais suportados incluem: Notebooks, Data Pipelines, Semantic Models (PBIP), Reports, Data Warehouses, Lakehouse schemas e KQL Databases. Sempre valide o suporte a itens experimentais antes de desenhar a topologia corporativa.

Resolução de Conflitos no Workspace

Quando um desenvolvedor altera um item no workspace enquanto outro desenvolvedor fez commit no mesmo arquivo no Git, o Fabric marca o item como Conflict. O usuário tem duas opções nativas:

  • Commit to Git: Força as alterações locais do workspace para o Git (sobrescrevendo o repositório).
  • Update from Git: Descarta as alterações locais do workspace e puxa a versão oficial do Git.

Internals: Serialização Declarativa & Projetos SQL (.sqlproj)

Por baixo dos panos, o Fabric serializa artefatos em pastas de metadados padronizados: 

Workspace-Root/
├── Notebook-Ingestion.Notebook/
│   ├── .platform
│   ├── item.metadata.json
│   └── notebook-content.py
├── Pipeline-Orders.DataPipeline/
│   ├── .platform
│   └── pipeline-content.json
└── Warehouse-Gold.Warehouse/
    └── .platform

Para SQL Database Projects, os arquivos DDL de tabelas e views são organizados em estruturas clássicas de .sqlproj. A pipeline do Azure DevOps executa SqlPackage.exe para gerar o arquivo de diferenças (DACPAC deploy) que aplica apenas as modificações estruturais nas tabelas do Data Warehouse, preservando os dados históricos existentes.

Visão Executiva, Governança & Eficiência Operacional (FinOps)

Implementar CI/CD e Deployment Pipelines reduz drasticamente o Mean Time to Recovery (MTTR) e evita incidentes caros causados por edições manuais em ambientes analíticos de missão crítica:

  • Eliminação do "Trabalho em Produção": Desenvolvedores e analistas não possuem permissões de escrita direta nos workspaces de Produção. O único caminho de publicação é a aprovação formal do Deployment Pipeline.
  • Auditoria e Conformidade Total (SOX / GDPR): Cada alteração analítica é rastreável a um Pull Request assinado, com autor, revisores e data no repositório corporativo.
  • Otimização de Custos de Capacidade: Ambientes de teste e desenvolvimento podem utilizar capacidades menores (ex: F2/F4) ou ser pausados fora do horário comercial, reservando capacidades de alta performance (F64+) para a produção.

Exercício Prático: CI/CD com Integração Git e Deployment Pipelines

Guia passo a passo para executar diretamente na plataforma em nuvem do Microsoft Fabric (ou em simulação local).

📋 Cenário do Laboratório

Configurar o ciclo de vida de desenvolvimento de software (DevOps) no Fabric, conectando workspaces ao Git e utilizando Deployment Pipelines de 3 estágios (Dev > Test > Prod) com regras de parâmetros de conexão.

🔑 Pré-requisitos para Execução no Portal

  • Navegador web moderno (Edge, Chrome ou Firefox).
  • Acesso ao portal Microsoft Fabric (app.fabric.microsoft.com).
  • Capacidade ativa do Fabric (licença Fabric Trial gratuita ou capacidade corporativa).
  • Um Workspace configurado no modo de capacidade Fabric.
1

Vincular o Workspace ao Repositório Git

  1. Nas configurações do Workspace, clique em Integração com Git (Git integration).
  2. Conecte à sua conta do Azure DevOps ou GitHub, selecione o repositório e a branch dev.
  3. Observe a barra de status de sincronização indicando alterações pendentes de commit.
2

Configurar o Pipeline de Implantação de 3 Estágios

  1. Crie um novo Deployment Pipeline.
  2. Atribua o workspace de Desenvolvimento ao estágio 1 (Dev), Teste ao estágio 2 (Test) e Produção ao estágio 3 (Prod).
  3. Configure Deployment Rules para substituir conexões de banco de dados e nomes de Lakehouses entre os estágios.
  4. Execute a promoção de artefatos de Dev para Test com validação automática.

Pontos Críticos para a Prática e para o Exame DP-700

📝 Síntese dos Pontos Críticos Aprendidos:

  1. Integração Nativa com Git: Permite sincronizar workspaces do Fabric com branches do Azure DevOps ou GitHub, rastreando alterações de código como código-fonte.
  2. Deployment Pipelines (3 Estágios): Automatiza a promoção controlada de artefatos entre os ambientes de Desenvolvimento (Dev), Teste (Test) e Produção (Prod).
  3. Deployment Rules (Regras de Parâmetros): Substitui automaticamente variáveis de conexão e nomes de Lakehouses para que o ambiente de teste aponte para dados de teste.
  4. Projetos SQL (SQL Projects): Permitem versionamento declarativo de esquemas do Data Warehouse com compilação e deploy via arquivos .sqlproj e dacpacs.
