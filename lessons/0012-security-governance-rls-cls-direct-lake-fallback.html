Segurança em Camadas no Microsoft Fabric: Do Tenant à Célula

Em ambientes corporativos analíticos unificados sobre o OneLake, a segurança não pode depender apenas de senhas de banco ou pastas de rede. O Microsoft Fabric implementa uma matriz de controle em profundidade que abrange permissões de colaboração, papéis granulares de dados e políticas de auditoria global com o Microsoft Purview.

O Dilema Arquitetural do Direct Lake Fallback no Power BI

Entenda por que a decisão de onde aplicar o Row-Level Security (RLS) define se o relatório voa em memória ou engasga no DirectQuery.

❌ Cenário Problemático: RLS no SQL Endpoint

A regra de RLS é criada via script T-SQL diretamente na tabela Delta do Lakehouse.

⚠️ CONSEQUÊNCIA: DIRECT LAKE FALLBACK

O motor VertiPaq do Power BI não consegue carregar os arquivos Parquet puros na memória (pois violaria a regra dinâmica de linha do SQL). O relatório é forçado a fazer Fallback para DirectQuery, convertendo cada clique em consultas SQL lentas.

✅ Padrão Recomendado: RLS no Semantic Model

A regra de RLS é criada diretamente nas funções DAX do Modelo Semântico do Power BI.

🚀 RESULTADO: VELOCIDADE MÁXIMA DIRECT LAKE

O Power BI acessa o OneLake utilizando uma identidade fixa gerenciada com permissão de leitura pura. Os arquivos Delta são carregados diretamente para a memória e o filtro de linha é avaliado pelas threads do VertiPaq em subsegundo!

Segurança Granular em T-SQL: RLS, CLS e DDM

  • Row-Level Security (RLS): Utiliza uma função com predicado de segurança (ex: WHERE Region = USER_NAME()) para filtrar linhas transparentemente.
  • Column-Level Security (CLS): Concede privilégios restritos (GRANT SELECT ON Tabela(Coluna1, Coluna2) TO Usuario), bloqueando colunas com salários ou identificadores sensíveis.
  • Dynamic Data Masking (DDM): Mascara dados pontuais (ex: email(), partial(1,"XXXX",0), default()) em tempo de execução sem corromper os dados originais no armazenamento.

🌱 Como Funciona a Segurança em Camadas?

Pense no Fabric como um prédio empresarial de segurança máxima:

  • Workspace Role: É o crachá da catraca na entrada do prédio (diz se você pode entrar como visitante [Viewer] ou se tem chave das salas de servidores [Contributor/Admin]).
  • Dynamic Data Masking (DDM): É como uma caneta tarja-preta digital: na tela do operador de telemarketing, o número do cartão de crédito aparece como XXXX-XXXX-XXXX-1234, mas no disco do banco o número verdadeiro continua salvo para processar pagamentos.
  • Direct Lake Fallback: É quando o elevador expresso para de funcionar porque a porta foi bloqueada com uma chave manual, obrigando todo mundo a subir de escada caracol (DirectQuery)!

🌿 Governança com Microsoft Purview e Endorsement de Dados

No Microsoft Fabric, você classifica a confiabilidade e sensibilidade dos artefatos através de:

  • Sensitivity Labels (Rótulos de Sensibilidade): Definidos no Purview (ex: Geral, Confidencial, Altamente Confidencial), aplicam criptografia que persiste mesmo se o usuário exportar uma tabela para Excel.
  • Endorsement (Chancela de Qualidade):
    • Promoted (Promovido): Marcador de que o dado foi validado pelo time do workspace e está pronto para consumo geral.
    • Certified (Certificado): Nível máximo de governança, exigindo aprovação formal de um comitê de governança do tenant para indicar que a tabela é a verdade canônica da empresa.

🛠️ Armadilhas de Prova DP-700: Fallback e Permissões de Workspace

⚠️ Questão Crítica de Prova: "A diretoria reporta que relatórios do Power BI em Direct Lake que costumavam carregar em menos de um segundo agora demoram mais de 30 segundos após a equipe de engenharia aplicar regras de Row-Level Security no SQL Analytics Endpoint do Lakehouse. O que causou a lentidão e como resolver?"

Causa Raiz: A aplicação de RLS no nível do SQL Analytics Endpoint impede que o VertiPaq carregue os arquivos Parquet puros na memória, forçando o Direct Lake Fallback para o modo DirectQuery.

Solução Recomendada pela Microsoft: Remover o RLS do SQL Endpoint e configurá-lo diretamente no Modelo Semântico do Power BI, configurando o relatório para autenticar com credencial fixa autorizada a ler a tabela no Lakehouse.

⚙️ Arquitetura Interna: OneLake Data Access Roles (Preview)

Tradicionalmente, conceder acesso de leitura a um workspace concedia visibilidade sobre todas as tabelas do Lakehouse.

Com as OneLake Data Access Roles:

  1. O administrador define papéis no nível de pastas de tabelas Delta individuais dentro do OneLake.
  2. Quando um motor (Spark ou VertiPaq) requisita o token OAuth do Microsoft Entra ID, o serviço do OneLake avalia as ACLs em nível de caminho de arquivo (Path-level ACLs).
  3. Isso permite implementar segurança granular diretamente no lago de dados sem depender exclusivamente de proxies SQL relacionais.

🏛️ Visão Estratégica & FinOps: Governança sem Impacto na Fatura

Em ecossistemas legados, implementar segurança e criptografia exigia appliances de firewall e proxies de segurança dedicados que aumentavam o TCO.

No Microsoft Fabric:

  • A criptografia em repouso e em trânsito é nativa e gerenciada pela nuvem Azure sem cobrar CUs adicionais.
  • A integração do Purview aplica governança contínua (LGPD/GDPR) evitando vazamentos de dados que poderiam acarretar multas milionárias para a empresa.

Exercício Prático: Implementar RLS, CLS e Mitigar Direct Lake Fallback

Guia passo a passo para executar diretamente na plataforma em nuvem do Microsoft Fabric (ou em simulação local).

📋 Cenário do Laboratório

Implementar segurança granular com Row-Level Security (RLS) e Column-Level Security (CLS) no SQL Analytics Endpoint e compreender o comportamento de Direct Lake Fallback no Power BI.

🔑 Pré-requisitos para Execução no Portal

  • Navegador web moderno (Edge, Chrome ou Firefox).
  • Acesso ao portal Microsoft Fabric (app.fabric.microsoft.com).
  • Capacidade ativa do Fabric (licença Fabric Trial gratuita ou capacidade corporativa).
  • Um Workspace configurado no modo de capacidade Fabric.
1

Criar a Função Predicado e a Política de Segurança (RLS)

  1. No SQL Analytics Endpoint ou Warehouse, abra uma consulta SQL.
  2. Crie a função inline table-valued que valida o usuário conectado via USER_NAME().
  3. Aplique a SECURITY POLICY com FILTER PREDICATE sobre a tabela de vendas.
🔒 https://app.fabric.microsoft.com/groups/security/rls-policy
📸 Captura do Portal: Definição de Security Policy em T-SQL e diagnóstico visual do efeito de Direct Lake Fallback.
2

Diagnosticar o Fallback de Direct Lake para DirectQuery

  1. Conecte um relatório do Power BI no Modo Direct Lake.
  2. Abra o Performance Analyzer e observe que a consulta sofre Fallback para DirectQuery porque o motor VertiPaq não processa RLS nativo do SQL Endpoint.
  3. Compreenda a recomendação do Fabric: para manter Direct Lake puro com subsegundo, configure o RLS diretamente no Modelo Semântico do Power BI.
⚠️ Atenção para o Exame DP-700:
Regra Fundamental do Exame DP-700: RLS ou CLS habilitados na camada SQL do Fabric provocam Fallback silencioso de Direct Lake para DirectQuery no Power BI. Para manter o modo Direct Lake de memória pura, implemente as regras de segurança no próprio Modelo Semântico.

Pontos Críticos para a Prática e para o Exame DP-700

📝 Síntese dos Pontos Críticos Aprendidos:

  1. Row-Level Security (RLS): Restringe quais registros um usuário pode visualizar com base em predicados de segurança (ex: região ou filial).
  2. Column-Level Security (CLS): Oculta ou bloqueia colunas sensíveis (como salários, CPF ou margens de lucro) de usuários não autorizados.
  3. Direct Lake Fallback: A presença de RLS ou CLS no SQL Endpoint força o Power BI a cair silenciosamente para o modo DirectQuery T-SQL, aumentando o consumo de CUs.
  4. Arquitetura Recomendada: Para preservar a performance de subsegundo do Direct Lake, aplique as regras de RLS no próprio Modelo Semântico do Power BI.
