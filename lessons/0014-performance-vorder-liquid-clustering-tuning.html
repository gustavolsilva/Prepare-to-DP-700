Maximizando Throughput e Minimizando Consumo de CUs no Fabric

Em ambientes analíticos sobre o OneLake, otimizar performance não é apenas uma questão de velocidade de resposta para os usuários do Power BI: é uma decisão direta de FinOps que evita o consumo desnecessário de Capacity Units (CUs) e previne o estrangulamento da capacidade (Throttling). A arquitetura do Microsoft Fabric introduz inovações profundas no formato de armazenamento e no gerenciamento de tabelas Delta.

Evolução da Organização Física: Z-Order vs. Liquid Clustering

Por que o Microsoft Fabric recomenda Liquid Clustering para tabelas de grande escala.

📦 1. Particionamento Estático & Z-Order

Padrão clássico de Data Lakes baseado em pastas rígidas (ex: /ano=2024/mes=10/) + OPTIMIZE Z-Order.

  • Overpartitioning: Cria milhões de arquivos pequenos quando a cardinalidade é alta.
  • Custo de Reescrita: O comando OPTIMIZE table ZORDER BY (...) reescreve todos os arquivos do cluster, consumindo muitas CUs.
  • Rigidez: Mudar as colunas de particionamento exige reescrever a tabela inteira do zero.

💧 2. Liquid Clustering (CLUSTER BY)

Nova geração de layout físico declarativo no protocolo Delta Lake nativo do Fabric.

  • Incremental & Eficiente: Apenas os dados novos ou alterados são reorganizados, economizando até 80% de tempo de escrita.
  • Alta Cardinalidade: Suporta colunas como IDs de clientes ou timestamps sem criar subpastas infinitas.
  • Evolução Dinâmica: Permite alterar as colunas de agrupamento com ALTER TABLE CLUSTER BY sem reescrever o histórico.

V-Order: Aceleração em Tempo de Escrita

O V-Order é um algoritmo de otimização no nível de escrita proprietário da Microsoft, mas totalmente aderente à especificação aberta do Apache Parquet. Ao gravar dados via Fabric Spark ou Data Warehouse:

  • As linhas dentro de cada Row Group são ordenadas e os metadados estatísticos (min/max) são organizados de modo a maximizar o Data Skipping.
  • Os dicionários colunares são alinhados à estrutura interna do motor VertiPaq do Power BI.
  • Benefício: Leituras no modo Direct Lake alcançam velocidades de subsegundo equivalentes à memória sem que os arquivos percam compatibilidade com bibliotecas abertas como DuckDB, PyArrow ou Polars.
⚠️ Alerta do Exame DP-700: Manutenção com VACUUM e Perda de Time Travel
O comando VACUUM limpa arquivos Parquet que não pertencem mais ao snapshot ativo do Delta Lake. O limiar de retenção padrão é de 7 dias (168 horas). Se você executar o VACUUM com retenção zero (RETAIN 0 HOURS), você não conseguirá mais consultar versões anteriores da tabela via Time Travel (TIMESTAMP AS OF ou VERSION AS OF).

Entendendo Otimização de Forma Simples

Imagine que o OneLake é uma imensa biblioteca de livros:

  • Sem V-Order: Os livros estão jogados aleatoriamente nas prateleiras. Para achar uma palavra, você precisa folhear página por página.
  • Com V-Order: Os livros estão em ordem alfabética e têm um índice no final. Você vai direto na página certa em um instante!
  • Z-Order vs. Liquid Clustering: No Z-Order, toda vez que chega um livro novo, você precisa reorganizar a estante inteira. No Liquid Clustering, a estante é elástica e só ajusta o cantinho onde o livro novo entrou.
  • VACUUM: É o caminhão de reciclagem. Ele recolhe os livros velhos rasgados. Mas se você mandar reciclar livros de ontem, nunca mais poderá reler o que foi escrito ontem (Time Travel)!

Implementação Prática de Tuning em SQL e Spark

Como aplicar as técnicas de otimização no dia a dia com T-SQL e PySpark:

1. Criando Tabela Delta com Liquid Clustering

-- Sintaxe Spark SQL no Fabric Notebook
CREATE TABLE bronze_orders (
    order_id BIGINT,
    customer_id STRING,
    order_date DATE,
    amount DECIMAL(10, 2)
)
USING DELTA
CLUSTER BY (customer_id, order_date);

-- Para re-otimizar periodicamente de forma incremental
OPTIMIZE bronze_orders;

2. Manutenção Segura com VACUUM

-- Remove arquivos órfãos mantendo 7 dias para Time Travel
VACUUM bronze_orders RETAIN 168 HOURS;

3. Mitigação de Data Skew no Apache Spark

Quando uma partição contém muito mais dados que as outras, utilize o recurso de Adaptive Query Execution (AQE): 

-- Habilitado por padrão no Fabric Spark
SET spark.sql.adaptive.enabled = true;
SET spark.sql.adaptive.skewJoin.enabled = true;

-- Ou via hint direto na consulta PySpark:
df_orders.hint("skew", "customer_id").join(df_customers, "customer_id")

Arquitetura de Tuning para o Exame DP-700

Checklist de armadilhas e decisões arquiteturais cobradas na prova:

  • V-Order está ligado por padrão: No Fabric, novos arquivos Parquet gerados pelo Spark e pelo Warehouse já possuem V-Order ativo. Não tente desativá-lo a menos que haja uma restrição severa de latência de escrita.
  • Z-Order em tabelas com frequentes updates: O exame questionará o aumento abusivo no tempo de jobs e consumo de CUs quando uma tabela particionada e Z-Ordered sofre muitas operações de MERGE. A recomendação correta é migrar para Liquid Clustering.
  • Small File Problem: O uso de OPTIMIZE sem Z-Order apenas compacta arquivos pequenos (bin-packing) em arquivos maiores de ~1GB, melhorando drasticamente consultas no Lakehouse.
  • Estatísticas no Data Warehouse: O motor T-SQL do Fabric mantém estatísticas automáticas. Em tabelas voláteis com consultas complexas, validar ou atualizar estatísticas manuais (CREATE STATISTICS) garante planos de execução eficientes.

Internals: Engenharia de Arquivos V-Order e Data Skipping

Como o V-Order opera no nível binário do arquivo Parquet:

O formato Parquet tradicional armazena dados em blocos chamados Row Groups contendo colunas comprimidas com Snappy ou ZSTD. Quando o VertiPaq do Power BI em Direct Lake lê esse arquivo, ele precisa decodificar os dicionários e reconstruir vetores em memória.

O algoritmo V-Order reorganiza os valores ordenando linhas de acordo com um algoritmo hierárquico multivariável. Isso produz:

  1. Dicionários de coluna menores e com maior taxa de compressão por repetição contígua (Run-Length Encoding).
  2. Metadados de cabeçalho e rodapé (Footer Metadata) com intervalos Min/Max muito mais estreitos, permitindo ao otimizador do Fabric descartar (skip) blocos inteiros de disco sem precisar ler um único byte dos dados brutos.

FinOps & Eficiência de Capacidade (Redução de TCO)

O impacto financeiro de um design analítico bem otimizado no Microsoft Fabric:

  • Evitar Upsizing Prematuro da Capacidade: Uma capacidade F64 que sofre lentidão frequentemente não precisa de upgrade para F128; quase sempre, o problema é falta de V-Order, arquivos pequenos (small files) ou particionamento incorreto gerando excesso de CUs.
  • Prevenção de Throttling e Rejeição de Relatórios: Consultas que leem arquivos compactados e com Liquid Clustering terminam em centenas de milissegundos, mantendo o consumo de CUs suavizado (Smoothing) abaixo do teto de 100%.
  • Custo de Armazenamento no OneLake: O V-Order reduz o volume físico dos dados em até 30% a 40%, diminuindo o custo recorrente de storage no Azure.

Pontos Críticos para a Prática e para o Exame DP-700

📝 Síntese dos Pontos Críticos Aprendidos:

  1. Liquid Clustering (CLUSTER BY): Substitui o particionamento Hive e Z-Order. Elimina problemas de arquivos pequenos e permite alterar chaves de agrupamento sem reescrever dados.
  2. Otimização V-Order: Ordena internamente os valores dentro de cada Row Group do arquivo Parquet, maximizando o Data Skipping no Power BI Direct Lake.
  3. Compactação com OPTIMIZE: Agrupa arquivos minúsculos em blocos ideais de 1GB (Bin-Packing), reduzindo o overhead de metadados em consultas analíticas.
  4. Limpeza Controlada com VACUUM: Remove fisicamente do disco arquivos obsoletos após expirar a janela de retenção, liberando espaço sem corromper transações ativas.
