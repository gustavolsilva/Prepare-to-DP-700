O Desafio Poliglota do Microsoft Fabric: T-SQL, PySpark e KQL

Diferente das plataformas legadas onde um único motor tentava resolver todas as demandas (e falhava em escala ou custo), o Microsoft Fabric adota uma abordagem poliglota sobre o mesmo armazenamento compartilhado no OneLake.

O Exame DP-700 não avalia apenas se você sabe escrever código, mas principalmente se você sabe qual motor escolher para cada requisito de negócio:

Matriz Arquitetural: Onde Cada Linguagem Brilha no Fabric

Linguagem Item do Fabric Ponto Forte Principal Cenário de Prova DP-700
T-SQL Fabric Data Warehouse & SQL Endpoint Transações ACID relacionais, DML nativo, Joins em Star Schema e governança com RLS/CLS. Camada Gold servida, comandos MERGE atômicos e relatórios corporativos.
PySpark Fabric Lakehouse Notebooks Processamento distribuído de petabytes, manipulação de JSON/XML, Machine Learning e Spark Streaming. Carga Bronze para Silver, tratamento de dados corrompidos e janelas complexas.

Fundamentos de Modelagem Dimensional: O Padrão Star Schema

O Star Schema é o padrão canônico para analytics. Ele organiza os dados em:

  • Tabelas de Fatos (Fact Tables): Registram eventos quantitativos do negócio (vendas, cliques, medições). Possuem alta granularidade, milhões de linhas e chaves estrangeiras.
  • Tabelas de Dimensões (Dimension Tables): Contêm o contexto descritivo (quem, quando, onde, o que). Exemplos: DimCustomer, DimProduct, DimDate.
  • Surrogate Keys (Chaves Artificiais): Chaves numéricas inteiras (ex: INTEGER IDENTITY(1,1)) criadas para identificar uma linha na dimensão, dissociadas da chave de negócio original (ex: CNPJ ou UUID). Isso reduz o tamanho dos índices e acelera brutalmente os joins colunares.

🌱 O que é Star Schema e Por Que Chaves Artificiais (Surrogate Keys) Ajudam?

Imagine que a sua empresa vende produtos para milhares de clientes. Se em cada linha de venda você repetisse o nome completo do cliente, o endereço, a cidade e o telefone, o arquivo ficaria gigantesco e pesado.

No Star Schema, criamos uma tabela de Clientes onde cada cliente ganha um número simples (1, 2, 3...). Na tabela de Vendas, guardamos apenas o número do cliente e o valor da compra. Esse número simples é a chamada Surrogate Key: ele economiza memória e permite que o computador cruze milhões de vendas em fração de segundos.

🌿 Sintaxe Comparada: Resolvendo a Mesma Agregação nas 3 Linguagens

Para agregar vendas por região e calcular ticket médio:

1. Em T-SQL (Data Warehouse): 
SELECT c.Region, COUNT(f.SalesKey) AS Total, SUM(f.SalesAmount) AS Revenue
FROM FactSales f
INNER JOIN DimCustomer c ON f.CustomerKey = c.CustomerKey
GROUP BY c.Region;
2. Em PySpark (Lakehouse): 
df_fact.join(df_cust, "CustomerKey") \
  .groupBy("Region") \
  .agg(count("SalesKey").alias("Total"), sum("SalesAmount").alias("Revenue"))
3. Em KQL (Eventhouse): 
FactSales
| lookup DimCustomer on CustomerKey
| summarize Total = count(), Revenue = sum(SalesAmount) by Region

🛠️ Armadilhas do DP-700: Star Schema vs. Snowflake Schema & KQL Operators

⚠️ Dica de Ouro para a Prova: A Microsoft desfavorece o Snowflake Schema (onde dimensões são normalizadas em sub-dimensões adicionais) para relatórios Power BI Direct Lake. O modelo estrela desnormalizado (Star Schema) simples e direto é a resposta correta em 100% dos cenários de modelagem analítica.

Operadores KQL Mais Cobrados na Prova:

  • summarize arg_max(Timestamp, Value) by SensorId: Recupera a leitura mais recente de cada dispositivo IoT.
  • make-series: Cria séries temporais preenchendo lacunas de tempo com valores padrão.
  • has vs contains: O operador has busca termos inteiros indexados (alta velocidade), enquanto contains faz varredura de substrings (lento). Na prova, sempre escolha has para strings indexadas.

⚙️ Arquitetura Interna: Otimização VertiPaq e Surrogate Keys Inteiras

O motor analítico em memória VertiPaq (compartilhado entre Power BI Direct Lake e Analysis Services) utiliza compressão de dicionário e Bit-Packing.

Quando uma chave de junção é um inteiro sequencial de 32 bits em vez de uma string alfanumérica GUID de 36 caracteres:

  • A estrutura de hash em memória é reduzida em até 75%.
  • As instruções SIMD dos processadores modernos conseguem avaliar blocos de chaves em paralelo diretamente nos registradores da CPU.

🏛️ Visão Estratégica & FinOps: O Custo de Não Escolher o Motor Correto

Um erro comum em empresas que adotam o Fabric é tentar usar clusters de Spark para consultas analíticas pontuais de relatórios ou usar o Data Warehouse relacional para ingerir milhões de linhas de logs por segundo.

Impacto Financeiro direto em Capacity Units (CUs):

  • Ingerir telemetria em tempo real no Eventhouse consome até 80% menos CUs do que manter um pipeline de Spark Streaming ligado 24/7.
  • Servir relatórios diretamente do Star Schema no Fabric Warehouse ou Lakehouse via Direct Lake elimina a necessidade de pagar por licenças dedicadas de bancos analíticos terceiros.

Exercício Prático: Modelagem Dimensional em Star Schema com T-SQL, PySpark e KQL

Guia passo a passo para executar diretamente na plataforma em nuvem do Microsoft Fabric (ou em simulação local).

📋 Cenário do Laboratório

A Fabrikam precisa estruturar um modelo dimensional em Star Schema (Tabela Fato e Dimensões) e comparar a performance e custo de consulta analítica entre as três linguagens fundamentais do Fabric: T-SQL, PySpark e KQL.

🔑 Pré-requisitos para Execução no Portal

  • Navegador web moderno (Edge, Chrome ou Firefox).
  • Acesso ao portal Microsoft Fabric (app.fabric.microsoft.com).
  • Capacidade ativa do Fabric (licença Fabric Trial gratuita ou capacidade corporativa).
  • Um Workspace configurado no modo de capacidade Fabric.
1

Modelar o Star Schema no Fabric Warehouse via T-SQL

  1. No Fabric Data Warehouse dw_sales_enterprise, clique em Nova consulta SQL.
  2. Execute o script de criação da Fato e Dimensões com chaves substitutas (Surrogate Keys):
T-SQL — STAR SCHEMA MICROSOFT FABRIC CODE EDITOR 
-- 1. Criação das Dimensões
CREATE TABLE dbo.DimCliente (
    ClienteSK INT IDENTITY(1,1) NOT NULL,
    ClienteBK VARCHAR(50) NOT NULL,
    NomeCliente VARCHAR(100) NOT NULL,
    Regiao VARCHAR(50) NOT NULL
);

-- 2. Tabela Fato
CREATE TABLE dbo.FactVendas (
    VendaID BIGINT NOT NULL,
    ClienteSK INT NOT NULL,
    DataKey INT NOT NULL,
    ValorTotal DECIMAL(12,2) NOT NULL,
    Quantidade INT NOT NULL
);
🔒 https://app.fabric.microsoft.com/groups/dw_sales_enterprise/star-schema
📸 Captura do Portal: Editor T-SQL do Warehouse com o modelo dimensional em Star Schema e integridade de chaves.
2

Transformar Dados e Gerar Chaves no PySpark

  1. Abra o Notebook Spark vinculado ao Lakehouse.
  2. Execute a célula PySpark gerando Surrogate Keys usando funções analíticas de janela (Window Functions):
PYTHON (PYSPARK) — NOTEBOOK MICROSOFT FABRIC CODE EDITOR 
from pyspark.sql.functions import monotonically_increasing_id, row_number
from pyspark.sql.window import Window

df_raw = spark.table("raw_clientes")
windowSpec = Window.orderBy("ClienteBK")
df_dim_cliente = df_raw.withColumn("ClienteSK", row_number().over(windowSpec))

df_dim_cliente.write.format("delta").mode("overwrite").saveAsTable("dim_cliente_gold")
print("✅ Dimensão com Surrogate Key gerada com sucesso!")
3

Consultar Telemetria com KQL no Eventhouse

  1. Acesse o Eventhouse evh_iot_telemetry.
  2. Abra o KQL Queryset e execute uma consulta analítica de série temporal de alta frequência:
KQL — EVENTHOUSE QUERYSET MICROSOFT FABRIC CODE EDITOR 
RawTelemetry
| where Timestamp > ago(24h)
| summarize MediaTemperatura = avg(Temperature), Pico = max(Temperature) by bin(Timestamp, 15m), DeviceId
| top 5 by Pico desc
🔒 https://app.fabric.microsoft.com/groups/evh_iot_telemetry/queryset
📸 Captura do Portal: KQL Queryset executando agregações de subsegundo sobre telemetria e séries temporais no Eventhouse.
⚠️ Atenção para o Exame DP-700:
Lembre-se para a prova: T-SQL é o motor padrão para Star Schema e joins relacionais; PySpark é ideal para transformações de dados semiestruturados e geração distribuída de chaves; KQL é o motor imbatível para séries temporais e telemetria de alta frequência.

Pontos Críticos para a Prática e para o Exame DP-700

📝 Síntese dos Pontos Críticos Aprendidos:

  1. Modelagem Star Schema: Fatos registram métricas numéricas acumuladas; Dimensões fornecem contexto filtrável com Chaves Substitutas (Surrogate Keys) geradas de forma sequencial ou hash.
  2. T-SQL no Warehouse: Linguagem obrigatória para transações ACID completas, integridade relacional, comandos MERGE atômicos e governança com RLS/CLS.
  3. PySpark no Lakehouse: Motor ideal para transformação distribuída de grandes volumes, processamento de dados semiestruturados (JSON) e engenharia de dados em lote.
  4. KQL no Eventhouse: Linguagem analítica imbatível para telemetria de IoT, logs e séries temporais com indexação total e consultas em milissegundos.
